## 2. P1（发布前应修）

### P1-1 `HookState` 强制回写绕过节流，启动期大量同步跨进程调用

- `HookState.java:81-89`（`installed` → `publish(true)`）、`HookState.java:91-99`（`markNotFound` → `publish(true)`）、`HookState.java:101-112`（`note` → `publish(true)`）；`HookState.java:192-197` 的 `force=true` 直接跳过 2 秒窗口。
- 每个 `HookKit.install` 成功都会触发一次；失败还会 `markNotFound + note` 两次。默认配置下启动期约 80~110 次 `ContentResolver.call`，且都在 `onPackageReady` 主线程；`HookState.java:228-241` 每次还会重新反射 `ActivityThread`。
- 影响：启动卡顿；模块 App 进程未运行时，首次 `call` 可能把模块 App 拉起（MIUI 会 `security reject start`），与文档“2 秒节流”不符（`CHANGELOG.md:13-14`）。
- 修复建议：`publish` 始终受节流约束，或安装结束后统一 `flush()` 一次；缓存 `targetContext()`；把 `buildJson + call` 放到工作线程。

### P1-2 UI-02 `addTab` 兜底可删光所有 tab，违反“至少保留 1 个”

- `TopTabHooks.java:248-269` 的 `addTab` 兜底：只要 `keepSet` 非空且当前 tab 标题不在集合内，就 `removeTab + removeTabView`（`TopTabHooks.java:255-261`）。
- `TopTabHooks.java:342-359` 的 `filterList` 在“过滤后为空”时返回 `null`，调用方保留原列表。于是出现组合失败：`keepSet` 非空但没有一个标题匹配（旧配置、手改配置、未来版本改名）→ 数据层回退全量 → 兜底把每个 tab 都删掉 → 顶部频道栏为空。
- 与 `strings.xml:70`、`README.md:51,84` 的“至少保留 1 个”矛盾。
- 修复建议：兜底只在“数据层确实过滤过”时启用；或记录过滤后的保留标题集合，仅移除明确隐藏项；无论如何不要移除最后一个 tab。

### P1-3 DexKit 兜底无候选校验，`findMethod` 第二段可能挂错方法

- `DexKitLocator.java:268-281`：`findClass` 直接 `list.get(0)`，不校验是否为目标包、是否含预期成员；多个候选时可能选错类（例如 `SettingActivity` 的 `showFMAtBottomTab` 锚点同时命中 `PersonalFMModeChangeManager`、`rh0.d`、`th0.h`、`xr1.l`）。
- `DexKitLocator.java:350-369`：`findMethod` 第二段只按 anchors 查询，不限类名/方法名/参数；`DexKitLocator.java:438-462` 在 `returnType == null` 时直接取第一个候选。`HookKit.findMethodWithAnchors`（`HookKit.java:136-158`）传入的 `returnType` 正是 `null`。
- 影响：硬编码失败时（未来版本、自检）可能把 hook 挂到无关方法；当前 9.6.08 硬编码可用，所以未触发，但这是兜底链路的安全底线。
- 修复建议：`findClass` 增加目标包/成员校验；`findMethod` 第二段限定在候选类或校验方法名/返回类型/参数；多候选且无法消歧时拒绝并 WARN。

### P1-4 UI-13 `onCreateView` 返回 null，与调研文档的 NPE 警告冲突且未真机验证

- `WidgetPushGuideHooks.java:73-91`：`onCreateView` 直接返回 `null`，不 `proceed`；`WidgetPushGuideHooks.java:93-109` 再用 `onActivityCreated` 调 `dismissAllowingStateLoss`。
- `docs/phase2/new-hook-points.md` 的 N-01 明确写“Fragment 返回 null 可能触发 NPE，建议 hook `onCreate` 后 `dismissAllowingStateLoss()` 或 hook `loadData`”。
- 本次反编译核对：`PushGuideCenterDialogFragment` 的 `onActivityCreated` 对 `getDialog()` 做了空判断，`DialogFragmentBase.onStart` 在 `mDialog == null` 时直接返回，因此**该宿主当前实现下大概率安全**；但 UI-13 未在 VERIFY-A 中做真机五步验证，且 `onActivityCreated` 的 catch（`WidgetPushGuideHooks.java:101-105`）会吞掉宿主异常。
- 修复建议：改用 `loadData`/`onCreate` 后 dismiss，或返回 0 尺寸 View；补真机验证；catch 中记录后 `proceed` 而不是直接返回 null。

### P1-5 AD-10 默认开启、跳过启动任务 `init`，且属于规划中的 P1 候选

## 3. P2（可排后，但建议在 1.2.0 前处理）

### 3.1 DexKit

1. **内联 anchor 仍大量是类名/方法名，不是 dex 字面量**
   - 例：`TopTabHooks.java:45,82,110,173,234`（`HomeTopTabInfo`/`canDelete`/`TabExtra`/`nowChannelItems`/`UserSettingDTO`/`tabDataList`/`newTab`）、`HomeBlockHooks.java:50,287`（`MixContainerData`/`DiscoveryBlockData`）、`HintHooks.java:34`（5 个 simpleName）、`SplashAdHooks.java:109,131,163`（`LoadingAdActivity` 等）、`StartupDelayHooks.java:21`（`redPageDelayTime`）、`AdReportHooks.java:23`（`monitorRequest`）。
   - 本次 dexsql 复核：`redPageDelayTime`、`UserSettingDTO`、`tabDataList`、`newTab`、`MixContainerData`、`DiscoveryBlockData`、`LoadingAdActivity`、`LoadingAdShakeHelper`、`StatisticImpl`、`LogMonitorConfigManager` 在字符串池中为 0 条；`HomeTopTabInfo`/`canDelete` 实际由 `HomeTopTabInfoJsonAdapter` 使用，`TabExtra`/`nowChannelItems` 实际由 `TabExtraJsonAdapter` 使用。即使硬编码失败，这些兜底也找不到目标类，或会找到 Adapter。
   - 建议：只保留 `DexKitAnchors` 中已验证的字面量；其余改用结构匹配（superClass/fields/methods）或删掉 anchors 参数；把 dexsql 锚点校验纳入 check-mounts。
2. **第三阶“从 APK 解压到目标 cacheDir 再 System.load”在 Android 10+ 大概率不可用**（`DexKitLocator.java:142-197`）。目标 App targetSdk 34，cacheDir 可写，`dlopen` 可写目录受限制；当前第一阶 `useLegacyPackaging` 已成功（VERIFY-A），第三阶未被验证。
3. **DexKit 查询仍可能落在主线程**（`DexKitLocator.java:256-290,319-375`）。只有自检路径会 `warmUpAsync`（`CloudMusicToolModule.java:74-79`）；非自检的兜底首次查询是同步的，只在 >300ms 时 WARN。建议默认异步预热或把安装移出主线程。
4. **预热线程与主线程可能并发查询同一个 bridge**（`DexKitLocator.java:390-409`）；`getBridge` 有锁，但 `bridge.findClass/findMethod` 无锁。建议预热完成后 join，或给查询加锁。
5. **类缓存只按 anchors 做 key**（`DexKitLocator.java:240-250`）；一旦某组 anchors 命中错误类，后续同 anchors 查询都会复用错误结果。

### 3.2 HookKit / HookState

6. **hit 限流按 Feature 而非挂载点**（`HookKit.java:311-327`）：同一 Feature 5 秒内只打第一条，UI-02 有 16 个挂载点，T0/Tc 等关键日志会丢（VERIFY-A:94-95 已自认）。建议按 label 限流，或每个 label 首次必打。
7. **返回类型校验只覆盖 `ConstBoolHooker`/`SkipVoidHooker`**（`HookKit.java:285-309`）：自定义 lambda（如 `AudioAdHooks.java:35-45`、`TopTabHooks.java:148-158`、`CommunityLiveHooks.java:77-87`）完全绕过校验。建议在调用点显式断言，或给 `install` 增加可选 `expectedReturnType`。
8. **`HookState.publish` 并发**（`HookState.java:192-226`）：`sLastPublish` 是普通 volatile，多个 hook 线程同时 hit 时可能都通过节流；`targetContext()` 每次反射。建议 `AtomicLong` + 缓存 Context。
9. **`:play` 进程会覆盖主进程状态**（`HookState.java:29-33`；`Hooks.java:46-54`）：两个进程写同一个 `hook_status` key，后写覆盖；9.6.08 `:play` 实测不存在，但其他版本/设备可能踩到。建议 JSON 带 process 字段并合并。
10. **诊断卡可能显示上次进程的陈旧状态**（`SettingsFragment.java:179-217`）：目标未运行时仍读取本地 `hook_status`。建议带 `updatedAt`/进程存活判断或显示“上次注入”。
11. **死代码**：`HookState.snapshotJson`（`HookState.java:125`）、`StatusProvider.clearState`（`StatusProvider.java:105`）、`HookKit.firstStringGetter`（`HookKit.java:412`）、`Anchors.java`（全文件无引用，注释还写“Phase 0-2 骨架”）。

### 3.3 StatusProvider

12. **exported 无权限**（`AndroidManifest.xml:23-28`；`StatusProvider.java:49-89`）：UID 校验逻辑正确（`getPackagesForUid` + 精确包名），未发现可绕过路径；但作为防御纵深，建议加自定义 signature/privileged 权限或至少加 `tools:ignore="ExportedContentProvider"` 注释。`query/insert/delete/update` 均返回空，未发现敏感信息泄漏。
13. **JSON 大小/并发**：64KB 上限在 `HookState.java:24,173-184` 与 `StatusProvider.java:32,59` 一致；`apply()` 并发安全。仅 `publish` 的节流竞态（见第 8 条）。

### 3.4 UI-02

14. **`removeTab` 后再 `removeTabView` 的顺序**（`TopTabHooks.java:259-260`）：若 `removeTab` 内部已把 `k.r` 置空，`removeTabView` 会拿不到预创建 View，空槽位仍可能残留。建议先 `removeTabView` 再 `removeTab`，或反编译确认 `removeTab` 是否已移除 View。
15. **同时 hook 多个 `addTab` 重载**（`TopTabHooks.java:238-269`）：外层 `addTab(k,I)` 内部会调用 `addTab(k)`，两者都被 hook，兜底逻辑可能对同一 tab 执行两次 remove；虽然大概率幂等，但存在索引/状态风险。建议只 hook 最底层 `addTab(k)`。
16. **`addTab(b,Z)` 也被 hook**（`TopTabHooks.java:238-248`）：`tabTitle` 对 `MusicTabLayout$b` 取不到标题，兜底无效；可显式跳过非 `$k` 首参。

### 3.5 新 hook 类

17. **`WidgetPushGuideHooks` 的 `onCreateView`/`onActivityCreated` 共用一个 try**（`WidgetPushGuideHooks.java:68-109`）：前者抛异常会跳过后者安装；`onActivityCreated` 的 catch 直接 `return null`，吞掉宿主异常（`WidgetPushGuideHooks.java:101-105`）。
18. **`CommunityLiveHooks#onBindViewHolder` 返回 null 且不 `proceed`**（`CommunityLiveHooks.java:77-87`）：对 void 方法是合法的，但 ViewHolder 可能被复用而保持旧绑定状态；当前把 `itemView` 置 GONE，视觉上可接受，建议注释说明。
19. **`StartupOrchestrationHooks` 的 priority 语义未验证**（`StartupOrchestrationHooks.java:19,115-145`）：代码假设宿主比较器升序、加 1000 即降优先级；本次未定位到排序实现。建议先只做 `runOnUIThread/degradeInit`，priority 待验证后再开。
20. **`StartupOrchestrationHooks.taskNameOf` 每次反射**（`StartupOrchestrationHooks.java:208-229`）：200+ 任务 × 3 个 hook 会重复 `getMethod`；建议缓存 `Class -> taskName`。
21. **PV-07 实际不可达**：`Config.java:30` 只从 remote prefs 读 `startup_task_blocklist`，没有默认值也没有 UI；`StartupOrchestrationHooks.java:60-76` 在空集合时直接返回。PV-03 有硬编码默认 3 项（`StartupBlacklistHooks.java:26-34`），PV-07 没有。建议要么复用 PV-03 默认值，要么明确“仅高级用户手改配置可用”。

### 3.6 check-mounts.sh

22. **方法引用会被算作 OK**（`tools/check-mounts.sh:23-42`）：`methods` 表同时包含方法定义和方法引用（`method_kind IS NULL`）。例如 `PlayerJankDialogHelper#showNMCacheIOErrorDialog` 的 3 条记录里只有 1 条是定义；如果定义被删、其他类仍引用，脚本仍报 OK。建议 SQL 加 `AND method_kind IS NOT NULL`。
23. **只查类+方法名，不查 arity/返回类型/版本**（`tools/check-mounts.sh:30-42`）：本次新增的 `CommentLiveViewHolder#onBindViewHolder` 等挂载点已用 dexsql 人工核对签名，但脚本本身不能防漂移。建议至少断言 arity/返回类型，并先 `aapt2 dump badging` 校验 versionCode=9006008。
24. **默认路径硬编码**（`tools/check-mounts.sh:7-8`）：`E:/download/base(2).apk`、`E:/tools/dexsql/dexsql.exe`。建议支持参数/环境变量（脚本已支持 `$1` 与 `DEXSQL`，但默认值仍不可移植）。
